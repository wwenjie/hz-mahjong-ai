  **自由匹配实测暴露的严重问题与修复**：10 场并发下 320 次动作尝试有 35 次（10.9%）被 409 `INVALID_ACTION` 拒绝，其中 20 次是出牌阶段；拒绝时刻距上一条日志记录的中位是 **2217ms**，而代码里「决策」与「提交」是相邻两行，说明提交在传输层被 429 退避重试（0.5s 起、最多 4 次）吃掉了整个窗口。压力来自每次动作要发 2 次请求（提交 + 提交后强制全量快照）。
  修复：`RateLimitedTransport` 新增**动作预留桶**——匹配 `POST .../action` 的请求只从预留桶取令牌，其余走主桶；两桶速率之和 = 总速率（总量不变，仍受平台 16/s 约束），预留比例下限保证轮询至少还剩一半；**预留桶为空时绝不回落主桶**（否则又会被轮询挤住、等于白留）。修复后同环境 **469 次尝试 0 拒绝**（基线 10.9%；该结果偶然出现的概率约 1e-23）
- [x] 3.14 可选实现 SSE 通知流作为加速手段（仅在长轮询频率成为瓶颈时启用） —— 客户端已实现并测试（`client/notify.py`，21 个单元测试覆盖帧解析、保活计数、`closed` 语义、断线重连、429 重试与 stop()）；真机验证了错误路径（对已结束场次返回 `404 GAME_NOT_FOUND`，被判为永久条件、**一次都不重连**），开心路径因通知流属玩家 API、而当时测试房对玩家 API 整体 404，只能用假流覆盖。
  **但结论是：不该接线**。现有循环用 30 秒长轮询——空闲时最多 30 秒一次请求、有事件时立刻返回，**每次更新本来就只花 1 次 `/state`**；而通知流收到帧后仍需 `GET /state?seq=本地` 拉增量，每次更新同样是 1 次请求。省下的只是空闲期空轮询（可忽略），`/state` 额度压力两种方案相同。因此接线的预期收益接近零，不值得为此动比赛路径上的代码。客户端保留，等日志里出现持续 `RATE_LIMITED` 时再启用

- [x] 6B.11 端到端验证：模型驱动 vs 固定常数驱动，以自对弈总得分作为最终判据 —— **已完成，结论为无显著差异（负结果）**。用 `tools/ab_test.py` 做配对检验：同种子重放同一副牌 + 四座位旋转，150 场 × 4 旋转 = 600 配对。五项指标全部不显著：总得分 +0.253（标准误 0.403，t 0.63，95%CI [−0.537, +1.043]）、名次分 +0.028、白板数 −0.008、胡次数 +0.007、番数总和 −0.007。**聚合的「+152 vs 0」是陷阱**——按旋转拆开为 −62 / −7 / +187 / +34，几乎全部来自旋转 2 一次的运气，这正是配对逐场检验的价值。信号仅为噪声的 1/40（每场差分标准差 ≈9.9，均值 0.25），要测显著需约 5800 配对（约 4 小时），而 +0.25 分/场无实战价值。
  **机制解释**：模型的输入与手写启发式高度重叠（`risk.py` 本就含 `+0.18 × progress` 与弃牌/副露项），且决策层阈值对 q 在两者输出区间内的差异不敏感。因此**默认档位保持 `heuristic`**，模型驱动留在 `--decider risk` 备用。
  **一项补做的诊断**（用于回答「模型到底学到什么」）：在 `progress` 分层**内部**计算 AUC，加权条件 AUC = **0.7558**（各层 0.52 / 0.80 / 0.86 / … / 0.75），即在固定牌局进度下对手行为特征仍有显著判别力——**6B 的模型本身有效，只是喂给阈值后不改变决策**
