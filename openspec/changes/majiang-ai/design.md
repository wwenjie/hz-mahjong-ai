# Design

## Context

目标产物是公司内杭州麻将 AI 竞技赛的参赛程序。约束来自赛事细则与平台接入指南（v34），其中影响架构的部分如下。

**时限与规模**

- 出牌思考 3 秒，碰窗口 1 秒、吃窗口 1 秒，且两个窗口固定走满。超时兜底：可胡时服务端自动胡（不丢番），否则自动打出最右侧一张牌。
- 每人同时参赛 M 场（自动房默认 M=10、每场 8 局；正式赛事由创建者配置），每场含若干局。
- 限速：状态轮询 16 次/秒/用户、并发挂起轮询 ≤32、自动匹配 10 次/分。
- 在线判据：最近 90 秒内有已认证请求，否则开赛时被剔除或按实到降档，实到不足 4 人则赛事作废。

**协议特性**

- 快照不含 `allowed_actions`，动作合法性全部由客户端自研判定。
- 每局结束固定停 5 秒（`phase="settled"`），此时快照中的手牌是上一局残牌，用于算牌会出错。
- 落后当前局或响应含缺口标记时返回全量快照；动作冲突后应重建快照。
- `stage_open` 阶段需重新确认出席，确认不跨阶段继承，晋级者未确认由候补递补。
- 平台中断时该阶段标记为待重赛，旧成绩清空、名单不变但确认重做。
- 平台可在正式比赛期间关闭自建测试房与自由匹配。

**规则特性**

- 只能自摸，不允许点炮，禁止抢杠胡。
- 白板即财神（百搭），可替代任意牌，但本身不能被吃、碰、杠、胡；打出财神触发抓打圈，封锁其余玩家的吃、碰、明杠并限制其只能打出刚摸到的牌。
- 总番为乘法连乘：`1 × 分支因子 × 2^动作链 × (4 白板 ×2) × (爆头 ×2)`，理论上限 512。
- 庄家 ×8，闲家 ×1；庄家自摸收三家各 ×8，闲家自摸时庄家付 ×8、另两闲各付 ×1。
- 牌墙最后 20 张不摸且禁止杠牌；吃最多 2 摊；七对禁止任何副露；流局庄家连庄。

**配置不可写死**

`BaseScore / M / Rounds / YouCaiBiKao / PengTimeoutSec / ChiTimeoutSec / DiscardTimeoutSec` 全部以运行时规则接口为准，每场赛事可能不同。

## Goals / Non-Goals

**Goals:**

- 交付能在 10/8 前提交、能在正式多阶段锦标赛中稳定参赛并自动完成全部决策的程序。
- 规则内核的判定口径与官方端点逐例一致，且该一致性可被自动化回归验证。
- 协议层对掉线、平台中断重赛、快照缺口与动作竞态具备自愈能力。
- 决策以阶段内总得分期望为目标，显式建模动作链乘法收益、庄闲赔付不对称、抓打圈封锁价值与流局归零。
- 具备离线自对弈与评测能力，使策略迭代不依赖正式比赛环境。

**Non-Goals:**

- 不做跨阶段的状态继承或长期学习（每阶段每场独立起算）。
- 不使用对手手牌等非公开信息。
- 不在正式比赛期间依赖平台测试房或自由匹配。
- 不在本次交付内追求端到端深度强化学习。

## Decisions

### D1 语言与进程模型：Python 单进程 + 线程池

平台官方示例是纯标准库 Python，因此传输层直接用 ``urllib``，不引入额外 HTTP 依赖。

- 选择：单进程，一个身份一个 ``Runtime``；每场对局一个线程（``ThreadPoolExecutor``），
  心跳由监督者循环的周期性请求承担。所有请求经同一个令牌桶，限速天然是「每用户全局」。
- **相对初稿的修正**：初稿写的是「asyncio 事件循环」。实际实现用线程池——因为传输层是
  阻塞式标准库实现，``asyncio`` 只会退化成「把阻塞调用丢给线程池」再包一层事件循环，
  没有收益。若将来改成异步传输（``aiohttp`` 之类），再引入事件循环才划算。
- 备选：多进程（每场一进程）——被否决，原因是无法在进程间共享限速额度，而平台限速是
  每用户全局的，多进程会让限速失效。
- 备选：Rust/C++ 决策核心 + Python 协议层——暂不采用。决策预算为 3 秒且并发场次有限，
  纯 Python 足以覆盖「规则引擎 + 启发式 + 轻量前瞻」，先把可交付性做扎实；若答辩需要
  更强的创新性叙事，可在 D5 的接口隔离下后置接入。

### D2 分层：规则内核 / 协议客户端 / 运行时 / 决策引擎

四层单向依赖：`决策引擎 → 规则引擎`、`运行时 → 协议客户端 + 决策引擎`，规则引擎不依赖任何 IO。

- 理由：规则内核是全系统唯一需要与官方口径对齐的部分，必须可脱离网络独立测试与对拍；决策引擎必须可独立替换以支撑答辩时的算法迭代。
- 备选：单一模块的大循环（接近官方示例）——被否决，原因是无法并发、无法测试。

### D3 协议以长轮询为主，SSE 为可选加速

- 选择：每场一个 `/state` 长轮询（无事件时挂起，最长约 30 秒），事件到达后再按需增量拉取。
- 理由：单次挂起请求天然把轮询频率压到限速以下，M 场并发时的挂起连接数远低于 32 上限。SSE 通知流只推送水位、不含内容，仍需回拉状态，收益有限，故列为可选。
- 风险：事件密集场次可能出现突发请求量，需要令牌桶削峰。

### D4 运行时无状态化：一切从快照重建

- 选择：不把任何仅存于本地的累计量作为推进依据；局面、局号、座位、响应状态在每次重建时以快照为准。
- 理由：平台存在阶段中断重赛、每局 5 秒停顿、跨局无事件等边界，本地累计极易与平台失步。
- 代价：每次动作后重建快照增加请求量，需靠长轮询与增量消费控制。

### D5 决策引擎以期望值评分为核心，算法可替换

- 选择：定义统一的处境结构与动作评估接口，先实现「规则引擎 + 期望值启发式」的基线，再迭代前瞻搜索与对手建模。
- 理由：交付优先。目标函数（总得分期望而非胡牌率）是本次比赛的核心创新点，其价值不依赖于具体算法，先用可解释的启发式把目标函数落地，答辩时也更易讲清。
- 备选：直接上 MCTS/自博弈——被否决为**首版**方案，原因是 3 秒预算跨 M 场并发分摊后余量有限，且缺乏本地模拟器时无法迭代。

### D6 官方番型端点作为测试 oracle，而非运行时依赖

- 选择：仅在对拍回归与歧义确认中使用 `POST /portal/api/tools/fan-calc`，线上决策不调用。
- 理由：该端点免认证但限速 10 次/秒/IP 且属外部依赖，纳入运行时会在比赛期间引入可用性风险；同时答辩时「自研结算校验」比「调用官方算分」更有说服力。

### D7 策略模式化：晋级轮稳健 / 决赛激进

- 选择：决策引擎按阶段切换目标函数。晋级轮在期望相近时降方差并兼顾名次分与白板获取数；决赛以总得分为唯一目标并计入同分加赛代价。
- 理由：晋级轮三键排序（总得分 → 名次分 → 白板获取数），决赛仅比总得分且同分自动加赛，两者最优策略不同。

### D8 凭据经环境变量注入

- 选择：令牌只从环境变量或启动参数读取，`.gitignore` 排除本地凭据文件。
- 理由：提交物会被代码审核，硬编码令牌既属安全风险也可能被判违规；服务端只存令牌哈希，泄露后无法找回。

### D9 编译产物与交付形态

- 选择：仓库形式交付，附依赖锁定文件与启动脚本；不使用 20M 压缩包形式。
- 理由：仓库形式可携带完整提交历史，便于审核，也便于冻结依赖保证「本地可稳定运行」。

### D10 目标函数重定义为期望得分，而非胡牌率

- 选择：决策目标为 `E[本阶段总得分]`。禁止以胡牌概率或听牌速度作为目标函数。
- 理由：番型为乘法连乘（上限 512），而总得分是加法累计，因此得分由**稀有的高倍率局主导**——一次 `三财飘 + 4 白板 + 爆头` 的收益量级相当于十余次平胡。「更快胡」与「更值钱地胡」在本平台上会给出相反的决策，必须先锁定前者。
- 推论：流局使全体归零，所以「避免流局」本身没有价值；只有当己方有自摸机会时，流局才是损失。
- 代价：期望值最大化天然偏好方差较大的路线，需由 D7 的模式层约束晋级轮的方差。

### D11 高杠杆子博弈用结构化求解，不做全局博弈论搜索

- 选择：把「弃胡飘 / 杠 / 胡」这一小组决策点当作独立的序贯决策问题求解，其余决策点用启发式评估。
- 理由：番型的乘法结构使得收益高度集中在这一点上；而全游戏的精确不完全信息求解（CFR 类）在麻将状态空间下不可行。
- 关键结论一（财飘停止规则）：设立即胡的得分为 `V`，`q = P(在我下次摸牌前无对手自摸)`。每飘一次的期望倍率因子为 `2q`，连续飘 n 次为 `(2q)ⁿ`。故最优策略是阈值策略：**`q > 0.5` 继续飘，`q ≤ 0.5` 立即胡**，到达动作链上限即停止。计入失败赔付 `L` 后的精确条件为 `q > (V + L) / (2V + L)`，说明**赔付越重阈值越高，庄家的飘阈值应高于闲家**。
- 关键结论二（杠优于飘）：杠同样使链 +1，但自带补牌——补牌是不经过任何对手回合的额外一次摸牌。故 **杠是「无暴露的 ×2」，飘是「暴露三个对手回合的 ×2」**；引擎应优先用杠堆链，仅在无杠可做时使用飘。
- 关键结论三（爆头入口）：`6 对 + 1 财神` 即为听任意（单张财神可与任意摸到的牌配成第 7 对），是本平台最廉价的爆头入口，也即财飘链的启动器；相比「4 张白板」门槛低得多。
- 备选：全游戏 CFR / 精确求解——被否决，状态空间不可行。备选：把子博弈也交给启发式——被否决，会丢掉本平台最大的收益杠杆。

### D12 路线分叉显式建模：七对+财飘 与 副露+杠链

- 选择：决策引擎同时维护两条互斥路线的价值估计并在每个决策点比较，而不是交给单一打分函数隐式混合。
- 理由：七对禁止任何吃碰杠，而副露正是杠链的来源，两者不可兼得且各自的链来源不同。

| 路线 | 链来源 | 爆头可达性 | 量级上限 | 代价 |
| --- | --- | --- | --- | --- |
| 七对 + 财神 | 飘 | 高（`6 对 + 1 财神` 即爆头） | 三豪华七对起 ×16 | 放弃全部副露，成牌速度慢 |
| 副露 + 杠 | 杠（暗 / 补 / 明） | 需 3–4 张财神，较难 | 平胡分支 3 连杠 + 三财飘 = ×256 | 副露暴露牌型，被迫放弃七对 |

- 备选：单一打分函数隐式权衡——被否决，实测中这类混合极易在关键分叉上取错方向。

### D13 抓打圈的时机语义与压制对象

- 选择：仅在己方成牌期望较低、且对手（优先庄家）尚未听牌时，才考虑以财神换取抓打圈。
- 理由一：**抓打圈挡不住自摸**。它只削弱仍在做牌的对手的推进速度，对已听牌的对手近乎无效。因此其价值集中在**早中期**，不能当尾盘保命符。
- 理由二：庄闲赔付不对称——闲家自摸收 `10F`，被庄家自摸赔 `8F`、被另一闲家自摸仅赔 `1F`。故**闲家的风险几乎全部集中在庄家的自摸上**，压制对象应是庄家；反过来庄家的赔率为 3:1（收 `24F` / 赔 `8F`），应更积极抢自摸而非防守。
- 代价：在非爆头态打财神会断链，等于用「一张财神 + 当前链」换取延缓对手，属于明确的资源交换，必须由期望值比较支撑。

### D14 对手自摸风险 q 用公开信息监督建模

**选择**：单独建立一个从公开信息估计对手自摸风险的模型，作为 D11 中 `q` 的唯一来源。**推理输入只用公开信息，训练标签可用完整手牌。**

**为什么可以这样做**：平台明确将测试房赛后事件流提供「供离线复盘与算法优化」，且该事件流包含四家开局手牌与逐事件动作——这是唯一能拿到「对手手牌」标签的渠道。合规红线约束的是**推理输入**，不是训练数据来源。

**建模目标**：不直接预测「对手下次摸牌是否自摸」，而是分解为两个因子后聚合。

```
每对手自摸风险      pᵢ = sᵢ × rᵢ
  听牌概率          sᵢ = P(对手 i 当前处于听牌，含听任意)
  条件自摸率        rᵢ = E[自摸张数] / 剩余可摸牌数
本圈无人自摸生存率  q  ≈ ∏(1 − pᵢ)
```

**为什么不用「自摸结果」作主标签**：平台允许弃胡。处于听牌（含听任意）的对手可能主动放弃胡牌去追动作链，因此「下次摸牌是否自摸」会**系统性低估**其威胁——越危险的对手越容易因为贪链而不胡。故主标签取「是否听牌」，该标签取自手牌状态，不受弃胡影响。

**已知偏差**：听任意状态在公开信息下不可完全观测（财神隐藏在手牌里），因此 `pᵢ` 会被低估、`q` 会被高估，方向上恰好导致**过度贪链**。应对：施加保守修正，使风险估计不偏高；并在端到端评测中用自对弈总得分验证修正幅度。

**特征集**（全部可由公开事件推导）

| 类别 | 特征 |
| --- | --- |
| 对手副露 | 副露总数、按类型计数（吃 / 碰 / 杠）、是否有杠（影响补牌次数） |
| 对手弃牌 | 弃牌数、花色分布、中段牌（2–8）占比、近期弃牌是否集中于单一花色 |
| 对手财神行为 | 该对手是否曾打出财神（意味着其手上曾有财神，且可能已触发抓打圈） |
| 全局资源 | 全局已消耗财神数、剩余可摸牌数、当前局号 |
| 己方状态 | 己方财神数、己方副露数、己方是否已听牌 |
| 局面 | 庄家座位、当前是否处于抓打圈、抓打圈豁免方 |

「剩余可摸牌数」是关键特征——自摸风险随剩余摸牌数单调变化，且该量可由公开事件精确计算：牌墙共 83 张，减去已摸张数，并在剩余 20 张保留牌时本局终止，故可摸上限为 63 张。

**样本定义**：以「决策时刻」为单位。每个样本 = （时刻、视角玩家、目标对手、该时刻的公开特征、标签）。每个样本的公开信息**必须仅由该时刻之前的事件推导**，禁止使用该时刻之后的信息或整局终态——这是最容易出错也最致命的一环。

**数据划分**：MUST 以局或房间为单位分组切分，**禁止在同一局内随机切分样本**。同一局的连续观测高度相关，样本级随机切分会把评估指标抬高到严重失真的程度。

**模型选型**：

- 主模型：梯度提升树（LightGBM / XGBoost）。理由是纯表格特征、样本量中等、训练快、无需 GPU、特征重要度可直接用于答辩。
- 对照：逻辑回归（可解释下限）、仅用「剩余可摸牌数」的单特征模型、固定常数。
- 不采用：序列深度模型（LSTM / Transformer）。数据量与时间预算都不支持，且可解释性差。

**评估协议**：

1. 概率质量：对数损失、布里尔分数、可靠性曲线。**注意不能只看 AUC**——模型的输出要直接与阈值比较，排序好但未校准的概率会给出错误的阈值决策。
2. 特征消融：逐组移除特征，输出各组贡献。
3. 端到端判据（最终标准）：模型驱动 vs 固定常数驱动，比自对弈总得分。

**烘焙与推理契约**：模型导出为小型树结构文件随仓库分发，推理用进程内实现，**确定性、无网络、无外部服务**。单次决策需对三家对手批量推理，耗时须可忽略。模型缺失或版本不兼容时回退到保守风险上界，使决策偏向立即胡牌。

**数据采集计划**：测试房配置为每场 8 局、M=10，则一轮约 80 局；每局约产生 190 个观察样本（4 个视角 × 约 48 次对手摸牌）。目标 **1000–2000 局**，即约 13–25 轮，估算 19 万–38 万样本，听牌正例率约 20–35%。采集需尽早启动，因为平台可在正式比赛期间关闭测试房。

**对手行为的多样性**：采集时必须让四个座位使用**不同的策略**（随机、向听贪心、七对贪心、副露贪心、以及主策略的混合）。若四家都用同一策略，行为分布单一，模型会在真实对手面前失效。

**反事实扩展（喂牌代价）**：出牌决策需要评估「若对手碰了这张牌，其自摸风险增加多少」。做法是把该对手的副露数加一后**重新推理**，取风险增量作为喂牌代价的一部分。该用法要求模型对副露数单调（副露增加则风险不降低），并作为回归测试项。

**附加收益**：该模型是答辩「AI 运用方式」维度的实证素材——有数据来源、有基线对照、有消融分析、有端到端效果。

## Risks / Trade-offs

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 规则口径存在文档歧义（4 白板爆头是否叠加、财神能否作胡牌张、`YouCaiBiKao` 是否开启） | 番型算错，策略系统性偏差 | 前两项已于 2026-09-23 对官方端点实测确认（叠加；可作胡牌张）并固化为回归用例与 `tools/fan_calc_diff.py` 对拍；`YouCaiBiKao` 运行时读取，两种分支都实现，其对局口径仍待验证 |
| 3 秒预算在 M 场并发下被摊薄 | 决策超时触发兜底，自动打最右一张 | 全局算力预算 + anytime 算法（到点返回当前最优）+ 保底动作 |
| 弃胡需显式提交，否则服务端自动胡 | 丢失财飘/杠链，番数大幅下降 | 弃胡路径纳入时限保障，作为独立高优先级决策分支 |
| 阶段中断重赛后旧成绩清空 | 本地状态与平台失步 | 无状态设计，全部从快照重建；重赛路径纳入演练 |
| 平台在比赛期间关闭测试房与自由匹配 | 无法实战验证 | 本地模拟器与批量自对弈作为主要评测手段，赛前完成实战验证 |
| 违规风险：使用对手手牌 | 直接除名 | 决策侧数据结构不承载对手手牌；代码审查项 |
| 官方端点或平台版本变更 | 接口行为变化 | 启动时版本自检，比对已知版本并告警破坏性变更；`tools/fan_calc_diff.py` 可随时重跑对拍 |
| 抓打圈内补杠是否放行未验证 | 动作合法性判错，触发 409 或漏掉合法动作 | 按「括号内为可用动作穷举」实现为禁用；番型端点无法覆盖该场景，待测试房对局实测 |
| 时间紧（10/8 截止） | 交付不完整 | 里程碑倒排：先打通「报名 → 到位 → 打完一整场」，再迭代策略；答辩材料与演示另行排期 |
| 目标函数选错（以胡牌率或听牌速度为优化目标） | 策略系统性偏弱，且四处局部决策相互矛盾 | 目标函数锁定为 `E[阶段总得分]`，并在评测中以总得分而非胡牌率作为对照指标 |
| 财飘阈值过度依赖 `q` 的估计精度 | 高估 `q` 会导致过度贪链，反而放大方差与失分 | `q` 用公开信息模型估计而非常数；阈值计入失败赔付 `L`；保留保守上限（估计不确定时按阈值下界决策） |
| 把抓打圈当作尾盘保命手段用于已听牌对手 | 白白消耗一张财神并断链，且毫无防守效果 | 抓打圈仅在对手未听牌时纳入候选；对已听牌对手不产生该项收益 |
| 显式路线分叉带来实现复杂度 | 决策代码膨胀，容易引入 bug | 两条路线各自以独立评估函数实现，最终只比较标量期望值；分歧点纳入复盘标注 |
| 测试房数据仅能赛前采集 | 对手模型缺少训练数据 | 采集任务前置到里程碑 B，并在平台关闭测试能力前完成数据落盘 |
