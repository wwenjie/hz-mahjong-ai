  对手的爆头率（22.7%）比我们还高，而他们只是赢得多——**爆头率与胜负是反向的**，
  这条应写进结论，避免以后有人再去追爆头。
- 但这两项机制差也都在 1 se 内（胡率 n=256 → se≈2.7pp；到听摸序 se≈0.22），**同样不达门槛**。

**判决：不采纳 v4，冠军保持 v3。** 理由是「弱且一致的正向迹象」不满足我事先写下的门槛
（三种子同向**且**显著、机制同向**且**超过噪声）。它与两拍的处理保持一致（都在机制不足时拒绝），
而不是「看着不错就上」。若日后拿到更强的机制量或更大样本，可重新评估。

### 2026-09-28 23:45 **更正**上面这条污染诊断里最要紧的一句

**我上一条说「每房 4.9 次被拒 ⇒ 每局约 0.5 次出牌不是我们打的」，这是错的。**
我在发布之后才去验**结果量**，结果不支持它：

| | v2 | v3 |
|---|---|---|
| 我们**实际打出的手数**/房（事件流） | 72.7 | **71.8** |
| 被拒提交/房（我们的日志） | 2.2 | 5.4 |

**实际出牌数几乎不变（−1.2%）⇒ 没有丢出牌。** 那些被拒的是**多余的提交**：
我们基于「上一局已经结束」的快照又提交了一次，平台拒掉。代价是浪费请求与速率额度，
**不是丢一手**。旁证：抽查的那次被拒，**1 毫秒后就有 `game.round` 事件**（局已换）。

**因此两条推论都要撤回**：
1. 「每局约 0.5 次出牌不是我们打的」——**不成立**；
2. 「修复 #2：`INVALID_ACTION` 重拉快照后重决一次，可能比任何策略微调都值」——**没有价值**，
   因为没有可恢复的丢失动作。**这条不要做。**

**留下的正确结论只有一条（仍然重要）**：被拒率是**延迟指标**——
CPU 竞争让我们的轮询落后、在过期快照上决策。它**不解释** v3 时代那 −2.15pp
（1.2σ，本来就在噪声内），也不构成「v3 变差」的证据。
**它唯一确凿的用途是：比赛期间不要在这台机器上跑重负载**，否则会浪费速率额度
（平台限速 16/s，我们本就贴着上限用）。

**我犯的错误类型（值得记）**：**先发布解释、后验证结果量**。
正确顺序是先测「有没有丢出牌」这个结果量，再谈机制。
这与今天早些时候那条「有预测力 ≠ 是好目标」是同源毛病：
**要检验的那一步必须放在解释之前。**
