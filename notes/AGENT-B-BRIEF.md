## 2. 为什么是你，而不是让 A 再干一份

A 在本轮已被后续数据推翻**四次**断言，每一次都是被数据纠正的，不是被推理纠正的：

| A 曾断言 | 实际 | 教训 |
|---|---|---|
| 自对弈显示「策略已到局部最优」 | 真机数据显示我们是最弱的打法 | **自对弈是有偏的判据** |
| 我们听牌率 83.6%，是活跃玩家最低 | 真值 21.3%；83.6% 是重建 bug 造成的假象 | 中间指标可能整体错 |
| `chase_baotou` 白丢胜率 | 反事实算出净赚 +3.8 分/局 | 假设要用反事实检验 |
| A/B 中 `no-chase` 有 2.8 点优势 | 只有 6 场/臂、p≈0.10，纯噪声 | 先看样本量再下结论 |

**并且 A 复算自己的数字时用的是自己写的脚本——同一个 bug 会在两处犯同样的错。**

所以你的第一要务是**独立复算**，而不是接受 A 的数字。你的第二要务是补 A 没时间碰的空白
（稳定性演练、提交物）。

**方法多样性比模型多样性更重要**：换个模型从同一个心智模型重写一遍同样的逻辑，很可能犯同一个错
（见第 4 节的三层验收）。

## 3. 硬约束（违反会造成真实损失）

1. **不要改** `src/majiang/strategy/**`、`src/majiang/runtime/**`、`src/majiang/sim/replay.py`。
   A 正在改这些文件；你改了会导致 A 的编辑冲突或覆盖。
2. **不要启动任何访问比赛平台的进程。** A 已经有两个长跑进程在用同一个令牌：
   - `auto_session.py`（自由匹配采集，pid 会变，`pgrep -af auto_session.py` 可查）
   - `watch_process.py`（稳定性采样）

   平台限速是**按用户** 16/s，A 的两个令牌桶加起来正好 14/s。你再加一个采集器会互相挤兑，
   正式比赛期间会直接 429。**需要动平台请先问 A。**
3. **不要杀 A 的进程**（`kill` / `pkill`）。要清理自己起的进程时，先用 pid 确认，
   `pgrep` 的匹配会命中自己的 bash wrapper，也会命中 A 的进程（踩过）。
4. **git 纪律**：提交前 `git pull --rebase`；**禁用** `git reset --hard`、`git checkout -- .`、
   `git clean -fd`（会抹掉 A 未提交的工作）。一次只提交一小块，commit message 说清「结论」而非「改了什么文件」。
5. **不要输出任何凭据**。令牌只从环境变量读，绝不写进文件、日志、命令行、commit。

## 4. 你的三件任务

完整细节在 `notes/HANDOFF.md`。这里给摘要。

### 任务 1（最高优先）：独立复算 A 的全部关键数字

**输入**：`data/auto_sessions/*/events/*.json`（约 1110 份，持续增长），我们的 user_id 是 `u_a7f7c67bb14a`。

**必须自己从原始 JSON 写代码**，不要 import `tools/measure_strength.py`、
`tools/analyze_declined_wins.py`、`src/majiang/sim/replay.py`。复用它们等于把同一个 bug 复制一遍。

要算的：手数/胜率、**公平份额 = 有胡率 ÷ 4**、每房四家排序下的名次分布与名次分（+3/+1/−1/−3）、
均番对比、每局副露次数（我们 vs 对手）、胡牌时已出牌手数。

A 报出的参考值（**不要拿来对齐**，不一致才是有价值的信息）：

| 指标 | A 的数字 |
|---|---|
| 手数 / 胜率 | 8,611 / 20.8% |
| 有胡率 / 公平份额 | 99.5% / 24.9% |
| 均番 | 1.268（其余玩家 1.316） |
| 名次分 | 平均 −1.31 分/房；第 1 名 7.2% / 第 4 名 44.1% |
| 副露/局 | 我们 0.59，对手 1.09 |
| 胡牌时已出牌手数 | 我们 7.8，对手 7.7 |

**已知的三个数据陷阱**（不处理你的数字一定错）：

1. **一份事件流是「一场 8 局」对局**，每局有**自己的起手手牌**（`blocks[].start_hands`）。
   局与局的边界**只能由 `blocks[].round_no` 变化判定**——事件流里**没有** `round_started` 事件。
   把 8 局的事件铺在同一局面上跑，第 2 局起全错，表现为「出牌时手上没有这张牌」占 34%、
   牌种超过 4 张（1110 局里 1109 局不满足守恒）。
2. `chi` 事件的 `data.tiles` **已包含**被吃的那张（实测 `["7b","8b","9b"]` 配 `tile="9b"`），
   再把它拼进副露会多一张。
3. **座位 0 是合法座位但 falsy**。写 `event.get("seat", -1) or -1` 会把座位 0 变成 −1，
   于是**座位 0 的每个事件都被丢弃**（A 踩过这个坑）。

**验收：三层，缺一不可**

- **结构性不变量**：每种牌全场合计 ≤ 4 张、总量 136，在全部文件上成立。
  这一层不依赖任何人的推理，是这次真正抓到 bug 的手段。**不要只靠「重新实现一遍」当验证。**
- **手算小样本对照**：随机挑 10 局，用眼睛核对脚本输出（手牌张数、副露、牌墙剩余、赢家）。
  系统性 bug（整体偏移一个座位、少算一局）只有这一层能抓出来。
- **不一致必须定位到具体局和事件**，不是「我的结果不同」。

## 6. 项目常识（省得你翻代码）

- Python 3.12，`uv` 管理，src 布局。`src/` **零第三方依赖**（纯标准库），numpy/sklearn 只用于离线训练。
- 目录：`src/majiang/rules/`（规则引擎）、`src/majiang/client/`（平台协议）、
  `src/majiang/runtime/`（并发对局循环）、`src/majiang/strategy/`（决策）、
  `src/majiang/sim/`（本地模拟器 + 事件流重建）、`tools/`（离线脚本）、`tests/`。
- 测试：`uv run pytest -q`（当前 412 passed，28 秒）。
- **平台规则要点**（和普通麻将不同，容易搞错）：**只能自摸，没有点炮、没有抢杠**；
  白板＝财神＝百搭，**财神不能被吃碰杠**，打出财神触发「抓打圈」（其余三家一圈内只能打刚摸到的牌、
  不能吃碰明杠）；吃牌全局最多 2 副；牌墙最后 20 张不摸不禁杠；流局庄家连庄。
  **番数是连乘的**（底 1 × 分支因子 × 2^动作链 × 4 白板 × 爆头），最高 512，所以分数分布极度重尾——
  **小样本的「每手平均分」不可靠，判断力要用低方差指标（胜率、听牌率）**。
